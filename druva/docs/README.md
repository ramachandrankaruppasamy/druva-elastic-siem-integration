# Druva Integration for Elastic

## Overview

Druva provides a cloud-native data security platform for protecting and recovering enterprise data across workloads.

The Druva integration for Elastic ingests and analyzes security, administrative, backup, recovery, data-access, unusual-data-activity, and cyber-resilience events from Druva Data Security Cloud.

The integration normalizes supported Druva event data into Elastic Common Schema (ECS) and Druva-specific fields, enabling security teams to investigate Druva activity alongside endpoint, identity, network, cloud, and other security telemetry in Elastic.

The package also includes nine prebuilt Kibana dashboards and 31 Elastic Security detection rules to help analysts investigate threats to protected data, monitor security and administrative activity, identify changes that could affect data protection or recoverability, and understand Druva activity during a security incident.

## What data does this integration collect?

### Event logs

The Druva integration processes event logs. It does not currently provide a metrics data stream.

The `event` data stream processes supported security, audit, administrative, data-protection, recovery, data-access, and cyber-resilience events generated by Druva.

Depending on the source event, normalized telemetry can include:

- Event type, timestamp, and severity
- Customer or tenant context
- User, service, and target identity information
- Authentication activity
- Administrative activity
- Protected resource and workload information
- Unusual Data Activity (UDA)
- File activity associated with UDA
- Security-control and configuration changes
- Backup and protection activity
- Restore, recovery, and rollback activity
- Data-access and operational actions
- Webhook configuration activity
- Alerts and other security-relevant activity

Field availability depends on the Druva event family and the attributes present in the source event.

## Data normalization

The integration normalizes supported Druva event attributes into ECS fields where appropriate and maps Druva-specific security, data-protection, recovery, and operational context into the `druva.*` namespace.

The ingest pipeline also supports the documented inSync SIEM event envelope and normalizes available SIEM event attributes into the same ECS and Druva field model used by the integration.

### Elastic Common Schema fields

Common ECS fields populated by the integration include:

| Field | Description |
|---|---|
| `@timestamp` | Timestamp associated with the Druva event |
| `event.id` | Unique identifier for the Druva event when available |
| `event.action` | Action represented by the event |
| `event.category` | ECS category assigned to the event |
| `event.type` | ECS event type |
| `event.outcome` | Outcome of the activity when available |
| `event.severity` | Severity associated with the event |
| `event.kind` | High-level event kind |
| `event.module` | Druva integration module |
| `event.dataset` | Druva event dataset |
| `user.id` | Identifier of the user or service identity when available |
| `user.name` | Name of the user performing the activity when available |
| `user.email` | Email address of the user when available |
| `user.target.id` | Identifier of the target identity when available |
| `user.target.name` | Name of the target identity when available |
| `user.target.email` | Email address of the target identity when available |
| `source.ip` | Source IP address associated with the activity when available |
| `destination.ip` | Destination IP address when available |
| `observer.vendor` | Vendor of the product producing the event |
| `observer.product` | Product producing the event |

Source IP addresses can also be enriched with ECS `source.geo.*` fields when geographic information is available.

### Druva-specific fields

Druva-specific context is mapped under the `druva.*` namespace.

Major field groups include:

| Namespace | Description |
|---|---|
| `druva.customer.*` | Druva customer or tenant context |
| `druva.feature` | Druva feature associated with the event |
| `druva.event_type` | Druva event type |
| `druva.resource.*` | Protected resource, workload, and parent-resource context |
| `druva.profile.*` | Druva profile information |
| `druva.alert.*` | Druva alert information |
| `druva.uda.*` | Unusual Data Activity context |
| `druva.file.*` | File activity associated with Druva events |
| `druva.webhook.*` | Webhook configuration and authentication context |
| `druva.operation.*` | Structured data-access, recovery, rollback, and other operational activity |
| `druva.change.*` | Structured configuration-change context |
| `druva.security.*` | Security-control state and security-impact context |
| `druva.backup.*` | Backup state and status |
| `druva.identity.*` | Druva SIEM identity context |
| `druva.publisher.*` | Druva SIEM publisher information |
| `druva.topic.*` | Druva SIEM topic information |
| `druva.schema.*` | Druva SIEM schema version information |
| `druva.activity` | Structured Druva administrative or operational activity |

Not every field is populated for every event. The fields available in a normalized document depend on the source event and the attributes supplied by Druva.

## Data stream

Supported Druva events are normalized into the following Elastic dataset:

| Property | Value |
|---|---|
| Data stream | `event` |
| Type | `logs` |
| Dataset | `druva.event` |
| Index pattern | `logs-druva.event-*` |

Druva data in this dataset can be used in Discover, Kibana dashboards, ES|QL queries, Elastic Security investigations, and detection rules.

## Security analytics

Druva telemetry provides security teams with context about identities, protected resources, security controls, data protection, backup activity, recovery operations, and activity affecting protected data.

The integration can help analysts investigate questions such as:

- Did suspicious authentication or administrative activity occur?
- Were privileged identities or administrative settings changed?
- Were security controls disabled or modified?
- Was unusual activity detected against protected data?
- Were suspicious data-access operations performed?
- Did backup or protection activity fail during an incident?
- Were recovery or rollback operations initiated?
- Which protected resources or workloads were affected?
- What sequence of Druva activity occurred during an investigation?
- What audit evidence is available for security or compliance review?

## Querying Druva data

Druva events can be queried using the `logs-druva.event-*` index pattern.

### Review recent Druva activity

```esql
FROM logs-druva.event-*
| KEEP @timestamp, event.action, event.category, event.outcome,
       user.name, druva.feature, druva.event_type,
       druva.resource.name
| SORT @timestamp DESC
| LIMIT 100
```

### Investigate Unusual Data Activity

```esql
FROM logs-druva.event-*
| WHERE druva.uda.type IS NOT NULL
| KEEP @timestamp, druva.alert.name, druva.uda.type,
       druva.resource.name, druva.resource.type,
       druva.file.created_count, druva.file.updated_count,
       druva.file.deleted_count, druva.file.encrypted_count
| SORT @timestamp DESC
```

### Review authentication activity

```esql
FROM logs-druva.event-*
| WHERE event.category == "authentication"
| KEEP @timestamp, event.action, event.outcome,
       user.id, user.name, user.email, source.ip,
       druva.event_type
| SORT @timestamp DESC
```

### Review security-control changes

```esql
FROM logs-druva.event-*
| WHERE druva.security.control IS NOT NULL
| KEEP @timestamp, event.action, user.name,
       druva.security.control, druva.security.previous_state,
       druva.security.current_state,
       druva.security.previous_enabled,
       druva.security.current_enabled,
       druva.security.impact
| SORT @timestamp DESC
```

### Review recovery and operational activity

```esql
FROM logs-druva.event-*
| WHERE druva.operation.type IS NOT NULL
| KEEP @timestamp, event.action, user.name,
       druva.operation.type, druva.operation.action,
       druva.resource.name, druva.resource.type,
       druva.operation.file_count,
       druva.operation.bytes_transferred
| SORT @timestamp DESC
```

## Getting started

This package provides the Druva ingest pipeline, field mappings, dashboards, and Elastic Security detection content.

The package does not define an Elastic Agent input stream. Druva event delivery to Elastic must therefore be configured separately from the package.

After Druva event delivery to Elastic is configured:

1. Verify that Druva events are being processed into `logs-druva.event-*`.
2. Confirm that `event.dataset` is `druva.event`.
3. Confirm that `event.module` is `druva`.
4. Verify that event timestamps fall within the expected Kibana search window.
5. Review normalized ECS and `druva.*` fields in Discover.
6. Review the included Druva dashboards.
7. Review the included detection rules and enable the rules appropriate for the environment.
8. Validate detection behavior against representative Druva activity before enabling rules broadly in production.

## Validation

After configuring event delivery, verify that:

- Events are arriving in `logs-druva.event-*`.
- `event.dataset` is `druva.event`.
- `event.module` is `druva`.
- Druva event timestamps fall within the expected search window.
- Expected ECS fields are populated for the applicable event family.
- Expected `druva.*` fields are populated when corresponding attributes are present in the source event.
- Dashboard visualizations return data for the selected time range.
- Detection rules have the event types and normalized fields required by their queries.

Because Druva event families contain different source attributes, not every normalized field is expected to be present on every event.

## Troubleshooting

### Events are not appearing

Confirm that Druva events are being delivered to Elastic and processed through the Druva event ingest pipeline.

Verify that resulting events are written to the `druva.event` dataset and that the event timestamps fall within the time range selected in Kibana.

### Dashboards show no data

First verify that events exist in:

`logs-druva.event-*`

Then:

1. Expand the Kibana time range.
2. Verify that the event families required by the visualization are present.
3. Confirm that the normalized fields used by the visualization are populated.

Some dashboard visualizations require specific Druva event families and can legitimately contain no data when the corresponding activity has not occurred.

### Detection rules are not generating alerts

Confirm that:

- The detection rule is enabled.
- The required Druva event family is being ingested.
- The normalized fields referenced by the rule are populated.
- The rule lookback window covers the relevant events.
- Any threshold, cardinality, correlation, or sequence conditions have been satisfied.

Some detections require specific activity patterns rather than a single Druva event.

### A normalized field is missing

Field availability depends on the source event.

Verify whether the corresponding attribute was supplied in the original Druva event and whether that event family is expected to populate the normalized field.

The ingest pipeline uses the source event during normalization and removes its temporary internal `json` structure after processing. The source payload is not retained as a `json.*` field hierarchy in the final normalized document.

### Historical events are not visible

Expand the Kibana time range and verify the event's `@timestamp`.

The normalized `@timestamp` represents the Druva event time and can differ from the time at which Elastic ingested the document.

## Security and data handling

The integration processes Druva event telemetry for use in Elastic.

Depending on the event type, telemetry can contain:

- User names and email addresses
- User, administrator, service, or API identity identifiers
- Source IP addresses
- Protected resource and workload names
- Customer or tenant identifiers
- Administrative activity
- Security configuration information
- Backup and recovery activity
- Data-access activity
- Alert and Unusual Data Activity information

Organizations should apply appropriate Elastic access controls, data-retention policies, and security practices based on their environment and data-governance requirements.

## Compatibility

The integration supports the Druva event structures handled by the included ingest pipeline, including the documented inSync SIEM event envelope.

Normalized field availability varies by event family because different Druva events provide different attributes.

When validating a deployment, use representative events from the Druva services, workloads, and event families enabled in the environment.
